# Backend review

Review only the requested scope and its connected callers/contracts. For instruction audits, inspect discovery, installed Boost behavior and actual loading evidence using [agent workflow](../../../docs/agent-workflow.md); also read `boost-maintenance` for integration changes. Paths and commands are relative to `backend/`.

- Read [architecture](../../../docs/architecture/overview.md), [naming](../../../docs/architecture/naming.md), relevant [patterns](../../../docs/architecture/design-patterns.md) and [conventions](../../../docs/architecture/conventions.md). Load [API](../../../docs/api/README.md), [security](../../../docs/security/README.md), [database](../../../docs/database/README.md), [domain](../../../docs/domain/README.md) or [testing](../../../docs/testing/README.md) only where the diff affects them. Existing product uncertainties must not become implicit decisions in a patch.
- Check the business owner and dependency direction before class shape. Extracted business code belongs in `Domain/<Domain>`; HTTP in `Http/*/Api/<Domain>`; Models/Policies stay conventional; Jobs/Events/Listeners are grouped by domain within native roots. Flag incorrect ownership, new global business Actions/Services/Queries, cycles (including through Model methods), copied owner rules or writes bypassing invariant-bearing operations. Evaluate a documented placement/collaboration exception on its actual benefit; do not flag intentional scoped Eloquent reads or direct concrete dependencies merely for crossing domains.
- Follow changed operations through actual routes/CLI/jobs, authorization, validated inputs, queries, transaction boundaries and public serialization. Check cross-user/related-ID access, privileged assignment, sensitive errors, exact values, concurrent mutation and duplicate/retry behavior where affected. Inspect failures and rollback, not only the happy path.
- Check Eloquent query growth, bounded pagination and native facilities before proposing another abstraction. An Action needs real orchestration/reuse; a Service needs a cohesive capability; a contract needs a seam. Also identify a missing pattern only when a simpler design fails current requirements. Check trivial Actions, generic Services, HTTP/domain leakage and excessive fragmentation as well as missing extraction. No finding solely because simple CRUD lacks a domain class, an Action, a unit test or another fashionable layer. Recommend subdivision only with cohesion/change-coupling evidence, not a file-count threshold.
- Examine meaningful proof: PostgreSQL integration for DB semantics, pure tests for calculations, external fakes for protocols, execution tests beyond queue/event dispatch. Run narrow non-destructive checks when available; distinguish execution from inspection and missing tests from proven bugs. Never reset a user's database for a review.
- Report actionable findings by severity with path/line, concrete trigger, user impact and smallest correction. Do not modify code unless asked. State when no defects are found, and identify material unverified behavior without claiming complete safety. Use the repository's cavecrew delegation rules when delegation applies.
