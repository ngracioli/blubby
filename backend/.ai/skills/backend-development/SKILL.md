# Backend development

Paths in this workflow are relative to `backend/`, even when the session starts at repository root. Read [architecture](../../../docs/architecture/overview.md), [naming](../../../docs/architecture/naming.md), the relevant [patterns](../../../docs/architecture/design-patterns.md), and [conventions](../../../docs/architecture/conventions.md). Do not load every topic by default.

1. Establish observable acceptance behavior, implemented versus planned state and the domain owning the requested outcome. Inspect related domain operations, routes, callers, tests, Models and sibling implementations. Reuse the existing owner when rules/change drivers are cohesive; create a new domain only for a real distinct capability, not one per endpoint/table. A simple CRUD can belong to a domain without creating a domain class or folder. Use [the docs map](../../../docs/README.md) to load API/security for HTTP work, database for persistence/concurrency, domain/MVP for financial rules, and operations for queued/external work. Resolve missing product rules before inventing behavior; continue independent work when possible.
2. Prefer available Boost MCP `application-info`, `database-schema` and package-filtered `search-docs` for relevant version/schema/API facts. Inspect actual exposed tools; if MCP is unavailable, state that and use installed source, Sail CLI and official versioned documentation. Do not install a second server or silently rely on newer docs.
3. Choose the smallest responsibility split using the architecture table. State why logic stays in the Controller or needs an Action/service/query/DTO/contract, including actor authorization, transaction ownership and failure/retry semantics where relevant. Use `Domain/<Domain>` for extracted business behavior and `Http/*/Api/<Domain>` for HTTP; keep Models/Policies conventional and framework Jobs/Events/Listeners domain-grouped in native roots. Do not generate global business Actions/Services/Queries. Read the ownership/dependency rules before cross-domain access: name collaborators, reuse owner rules, avoid cycles and identify one transaction owner. Add no interface/event solely to cross a folder. Create no speculative modules or wrappers. Any adopted pattern needs concrete participants, rejected simpler alternative and proof in the owning feature documentation.
4. For a bug or behavior change, write and run the smallest observable test first; verify failure is the intended behavior gap. Do not implement until that failure is confirmed. If meaningful proof cannot run, explain and ask how to proceed. For a pure refactor, run relevant existing tests before editing. Read [testing](../../../docs/testing/README.md) for PostgreSQL and factories: HTTP tests in `Feature/Api/<Domain>`, non-HTTP DB use cases in `Feature/Domain/<Owner>`, pure rules in `Unit/Domain/<Domain>`. Test observable behavior, not an artificial unit test for simple delegation.
5. Implement only required participants with native Laravel facilities and existing dependencies. Inspect Artisan generator help; use Sail and noninteractive generators. Keep request/response details outside application operations, enforce resource access at every entry point, keep atomic effects together and avoid irreversible I/O in retrying transactions. Update actual callers, fixtures, discovery/bindings and affected contract documentation.
6. Rerun the focused proof and relevant existing suite. Run Pint for changed PHP; Biome only for configured supported files. Run migration/build checks only when their inputs require them. Review placement/namespaces, documented ownership and dependencies, duplicated rules, unnecessary fragmentation, query growth, mass assignment, cross-user access, consistency and retry paths relevant to this change. Prefer real persistence tests and native external fakes over interfaces created solely for mocks.
7. Report changed behavior, actual checks/results and remaining limits. For nontrivial behavior/refactors, include one sentence naming the pattern reused/adopted or why a simpler approach suffices. Stop when acceptance behavior and relevant contracts are proven; no unrelated cleanup.
