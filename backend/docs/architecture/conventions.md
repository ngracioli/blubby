# PHP and Laravel conventions

Read this for implementation and refactoring; [architecture](overview.md) owns responsibility and extraction decisions. These are project rules, not claims that Laravel mandates Actions or services.

## PHP 8.5

- Follow Pint and sibling style. Type parameters, properties and returns; preserve framework-compatible signatures. Use PHPDoc for collection generics and meaningful array shapes, not duplicate prose. Avoid `mixed` where the contract is known.
- Prefer small cohesive functions and composition. SOLID guides substitutability and responsibility; it does not require one interface per class. DRY applies to repeated knowledge, not coincidentally similar syntax. KISS/YAGNI reject unneeded layers and customization points.
- Use promoted constructor dependencies. Inject concrete capabilities unless an actual contract is warranted. Prefer `final` for new leaf application classes without a supported extension point; preserve Eloquent/framework extension conventions. Do not introduce abstract base controllers/services for shared CRUD.
- Use backed enums for a closed supported set with meaningful behavior, not a replacement for configurable database data. Enum cases use TitleCase, following Boost. A state enum alone does not validate transitions.
- Plain `final readonly class ...Data` is enough for a justified DTO. `readonly` prevents property reassignment, not mutation of referenced objects; prefer immutable date objects for snapshots. Eloquent models are mutable and must not be readonly. Value objects validate invariants at construction and compare by value.
- PHP 8.5 pipe syntax, clone changes and property hooks are available language features, not architecture requirements. Prefer ordinary calls/properties when clearer; do not bypass Eloquent accessors/casts. Do not raise Composer's PHP constraint incidentally; Docker and CI execute 8.5 but `composer.json` still says `^8.3`.
- Catch exceptions only to recover, add safe context or translate a concrete boundary failure. Never return success after swallowing `Throwable`. Keep the previous exception when translating; do not expose SQL/provider credentials. Use Laravel validation, authorization and model-not-found exceptions for their existing HTTP semantics. Centralize custom rendering in `bootstrap/app.php`, not repeated controller try/catch.

Language references: [PHP 8.5](https://www.php.net/releases/8.5/en.php), [readonly properties](https://www.php.net/manual/en/language.oop5.properties.php#language.oop5.properties.readonly-properties), [enums](https://www.php.net/manual/en/language.enumerations.php).

## Laravel 13

- Classify each feature by its owning domain before generation. Extracted business Actions, services, queries and domain types go under `app/Domain/<Domain>/`; use the same owner for corresponding HTTP and test groupings. Do not create new global business `Actions`, `Services` or `Queries` directories. A simple CRUD may need no domain class. [Ownership and dependencies](overview.md#domain-ownership-and-dependencies) govern direct cross-domain calls and writes; they are not optional because Models remain globally namespaced.
- Keep Controllers, Requests and Resources under their respective `Http/*/Api/<Domain>` paths; keep Eloquent Models and Policies conventional initially. Jobs/Events/Listeners use Laravel roots with domain subfolders and delegate meaningful business behavior to its owner. Domain code may depend on Eloquent/Laravel, but never on `App\Http` or HTTP request globals. Before subdivision or a placement exception, document the concrete gain and discovery/caller implications in the owning feature docs.

- Generate supported participants with Sail Artisan `make:*`; inspect `--help` first and use `--no-interaction`. Use `make:class` for plain Actions/DTOs. Do not add a generator package. Place only needed files using [the directory reference](overview.md#directory-reference).
- Keep Models focused on entity behavior and persistence metadata. Match `User`'s Laravel 13 `#[Fillable]`, `#[Hidden]` and `casts(): array` convention for new models. Set fillable attributes deliberately, and assign privileged/ownership fields server-side. Use relationship return types and foreign keys. Hidden fields are defense in depth, not the public response contract.
- Use explicit eager loading for relationships the response needs, `withCount`/aggregates instead of loading full collections, and selected columns including required keys. Do not access unloaded relations in serialization loops. For relevant endpoint tests, prove query growth stays bounded as results grow; consider lazy-loading prevention in development when introduced in a separate behavior-tested change.
- Reuse local scopes for predicates, a model-specific builder for a reusable query vocabulary, and query classes for substantial reports. Match Laravel 13/sibling scope syntax; inspect Boost docs rather than copying an older-version example. Never hide per-user filtering solely in an undocumented global scope.
- Form Requests own nontrivial request validation and policy delegation. Inline `$request->validate()` remains acceptable for a truly small local operation. Use only validated, allowlisted input; explicitly constrain nested array keys. Authorization must protect the resource, not merely validate its ID.
- Policies own resource access, Gates own operations not tied to a resource. Plain scaffold controllers do not guarantee an `authorize()` helper; prefer `Gate::authorize()` or a Request's policy delegation. Do not create a custom authorization framework.
- Resources own public fields, conditional relationships (`whenLoaded`) and serialization; they do not query or write. See [API](../api/README.md) for envelopes and compatibility.
- Providers register bindings and boot framework integration. No business workflows or database/network I/O during registration. Do not bind auto-resolvable concrete classes gratuitously. No mutable per-user state in singleton services, especially in long-lived workers.
- Events name completed facts; listeners name reactions; Jobs name deferred operations. Keep required financial effects in the owning transaction, not Eloquent observers. Use native Laravel events, middleware, Pipeline, container and HTTP client before custom dispatch infrastructure.
- Configuration belongs in `config/`; application code reads `config()`, not `env()`. Keep secrets in environment injection. Defaults must work with current local/database drivers; do not assume Redis, AWS or cloud credentials from scaffold config keys.
- For a real external integration, isolate protocol mapping and validate remote data. Use Laravel HTTP client timeouts, explicit error handling and `Http::fake()` tests. Retry only when safe, with idempotency for remote writes; do not keep a database transaction open during a network call. Add an Adapter only for a concrete mismatch, not an imagined future provider.
- Factories provide minimal valid models and named states for distinct scenarios. Seeders provide explicit reference/development data, never implicit production credentials. Keep factory and policy discovery working when namespaces change. Migrations, exact values and integrity belong to [database](../database/README.md).

Native references: [Eloquent](https://laravel.com/docs/13.x/eloquent), [relationships](https://laravel.com/docs/13.x/eloquent-relationships), [validation](https://laravel.com/docs/13.x/validation), [authorization](https://laravel.com/docs/13.x/authorization), [container](https://laravel.com/docs/13.x/container). Consult package-compatible documentation through Boost before API-dependent edits.
